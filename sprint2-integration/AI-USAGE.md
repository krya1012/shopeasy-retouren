## Checklist Sprint 2 (team)

A result is entered here only after someone has really checked the contents.

1. `TASK-ANALYSIS.md`: everyone reads it and checks whether it reproduces the task (PDF) correctly. The proposals in section 5 (rules, errors, status changes) are proposals of the AI and must be agreed by the team.
2. Questions 1 to 3 in section 7 are answered by the lecturer. Yaraslau Krautsou (or someone else from the team) asks the lecturer questions 4 to 6.
3. The code of the three components: everyone reads it and can explain what it does (the lecturer asks questions about it). The new Javadoc comments help; everyone reads the ones of their part. Everyone starts the demo themselves following `README.md` and sees that it works.
4. The team agrees or changes: Java and RabbitMQ, the condition rules (README, section 2), the status changes (README, section 3, they also apply to `PATCH` in the REST mock with 409), the rule for `original_packaging` (only a lower score) and the assumption that the Java consumer does not call the REST mock (question 4; the PHP consumer of the portal does). The lecturer confirmed "all or nothing" for the batch check, the Java options in the `.proto` and the format of the order data.
5. The team decides who presents which component (table in `DEMO-SCRIPT.md`), plays the demo once completely and measures the time.
6. The portal (`selfservice-portal/`): the team agrees to use PHP/Laravel and Vue (DoD point 1). Everyone reads `StatusEventHandler.php` and `ReturnPolicy.php` and can explain them; one 30-minute walk-through is planned. Without agreement the folder is not merged.
